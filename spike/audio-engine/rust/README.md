## The three ownership rules, and where they are enforced

Everything above `engine.rs` is written in safe Rust and cannot get these wrong.
That is the point of the module existing.

1. **Strings are copied, then released.** `OwnedEngineString::drop` calls
   `NAE_FreeString`; `take()` copies into a Rust `String` first. Nothing outside
   `engine.rs` ever holds a `char*`. This matters because the DLL and this crate
   have separate heaps — the engine's `malloc` is not Rust's allocator.
2. **Handles are owned by `Stream`.** Its `Drop` calls `NAE_Close`, so an early
   return or a `?` cannot leak a COM interface.
3. **`Stream` is `!Send`.** An exclusive WASAPI stream belongs to the thread
   whose COM apartment created it. Making it `Send` would let a future refactor
   move one across threads and reproduce the apartment-lifetime crash the C++
   spike hit.

## Bugs this layer caught

The C++ harness could not have found these, which is the argument for having a
second consumer.

### Double free in the string wrapper

`OwnedEngineString::take` called `NAE_FreeString` inline *and* left `self` alive,
so `Drop` freed the same pointer again. Symptom was heap corruption
(`0xC0000374`) in the very next allocation, in a completely unrelated place.

The rule that fixes it: **one owner, one release, in `Drop` only.** Explicit
frees next to a `Drop` implementation are always a bug waiting to happen.

### camelCase / snake_case field mismatch

The C++ emitter writes `sampleRate`; the Rust struct said `sample_rate`, and
serde failed with `missing field`. Fixed with
`#[serde(rename_all = "camelCase")]` so the wire format stays camelCase while
the Rust API stays idiomatic. The wire format is not an API.

## Not a bug: the mangled Chinese device name

Early runs showed `扬声�?(网易虚拟音频设备)`. That is **PowerShell**, not the
engine. Verified by capturing raw stdout with `cmd /c` redirection, which
bypasses the console codepage, and decoding the bytes directly:

```
emitted:  U+626C U+58F0 U+5668 U+7F51 U+6613 U+865A U+62DF U+97F3 U+9891 U+8BBE U+5907
expected: 扬声器 网易虚拟音频设备
```

An exact match. `WideCharToMultiByte(CP_UTF8, ...)` on the C++ side,
`to_str()` in Rust, and `serde_json` all agree the bytes are valid UTF-8. If you
see mojibake in these logs again, check the shell before touching the code.

## Toolchain note

Rust uses the **GNU** toolchain (`x86_64-pc-windows-gnu`), matching the MinGW
that builds `nae.dll`. rustup's default on Windows is MSVC, which would have
required installing Visual C++ Build Tools for no benefit — the two sides meet
at a C ABI and never share a compiler.

`build.rs` links `libnae.dll.a`, the DLL's *import library*. This makes the
linker resolve all nine `NAE_*` symbols at compile time, so a renamed or removed
export breaks the build instead of failing at runtime. Before the export
surface was fixed up, that import library was 2.9 MB of real code rather than
import stubs; see the note in the parent README.

## Known gaps

- `src/ffi.rs` is hand-written rather than generated by bindgen, which avoids a
  libclang dependency. It now mirrors the analysis and session structs as well;
  every mirrored struct pins its offsets with `offset_of!`, and the C++ side
  pins the same literals with `static_assert`. Revisit bindgen if the surface
  grows much further.
- The device list crosses the boundary as JSON. Fine for a handful of devices,
  but this must **not** become the transport for audio samples, a spectrum
  stream, or anything on the realtime path — serialising those would defeat the
  whole point of keeping samples inside the DLL.
- `Stream` is still the blocking render primitive. Production playback uses
  `Session`, which owns the playback thread; `base/` wraps `Session`. `Stream`
  remains for the harnesses and low-level probes.
