### 1.1 macOS 设备丢失

之前 `deviceLost()` 恒为 `false`——`lost` 从来没有被置位，所以引擎里
`NAE_ERR_DEVICE_LOST`（暂停播放、保住句柄和位置）那条路径在 macOS 上是死代码。

现在在 `kAudioDevicePropertyDeviceIsAlive` 上装监听，设备消失时置位；
`AudioOutputUnitStart` 失败且设备已不在时也置位。

**诚实标注**：监听真正触发的路径没法在没有拔线的情况下验证。已验证的是
"不会误报"（播放、输出流两项检查全过）和原语本身（无效 id 判为不存活）。
真正的拔线验证要等硬件。

### 1.2 LGPL

两个平台的系统包都是 GPL（scoop 与 Homebrew 都带 `--enable-gpl`）。现在：

- CMake 优先用 `vendor/ffmpeg-lgpl`；
- `NEIRO_REQUIRE_LGPL` 默认开启，配置期读 `<root>/bin/ffmpeg -version`，见到
  `--enable-gpl` / `--enable-nonfree` 就拒绝配置；
- `scripts/build-lgpl.ps1`（Windows，下载 BtbN 预编译）与
  `scripts/build-ffmpeg-lgpl-macos.sh`（macOS，源码构建，111 秒）把树放进
  `vendor/ffmpeg-lgpl`。

### 1.3 CI

`scripts/verify.ps1` / `verify.sh` 做同一组事：配置、构建、无设备检查、
Base 的 `transport_check` 与 `index_probe`、binding 构建。
`-WithDevices` / `--with-devices` 追加需要声卡的检查。
工作流只做三件事：装工具链、取 LGPL FFmpeg、调脚本。

跑在 runner 上会怎样**没有验证过**（这里没有 GitHub runner）；能验证的是脚本本身，
两端都实跑到了 `PASS`。这是这份报告里唯一一处"写了但没在目标环境跑过"的东西。

### 1.4 Base 曲库索引

新增 SQLite v4/v5 表 `tags`：标题、艺术家、专辑、专辑艺术家、碟号、曲号、年份、
流派、时长、采样率、位深、声道，外加一列 Rust 侧折叠过的 `search_text`。

新增命令：`list_tracks` / `list_albums` / `list_artists` / `search` / `index_tags`，
对应事件同名。

填充者：扫描（新增与修改的文件）与标签写入（先删行再重读）。
一个工作线程，控制线程写库，整批一个事务。

**为什么要有它**：在此之前 UI 想显示专辑，只能对每首歌调 `read_tags`——
一万首唱片就是启动时一万次开文件。

## 3. 蓝队审查：结论与处理

两个窄范围审查（macOS 后端 + 许可门禁；Base 索引），共 21 条。
每条都先对照代码确认，再决定改或留。

### 3.1 确认为真并已修

引擎（`backend_coreaudio.cpp`）：

1. **`resume()` 不置 `running`**（BLOCKER）。`stop()` 用 `running.exchange(false)`
   决定是否调 `AudioOutputUnitStop`；`stop→resume` 之后 `running` 还是 false，
   析构时跳过停止，直接 dispose 一个 HAL 仍在回调的 unit。已修。
2. **`supportedShareModes` 被覆盖成只有 shared**（MAJOR）。前一行刚把两种模式都
   设好，几行后又被赋成 `1u << SHARED`，同时 `exclusiveSupported=1`，
   宿主读到的两个字段互相矛盾。已删掉那次覆盖。
3. **`std::stoul` 解析设备 id 会抛异常**（MAJOR），异常穿过 C ABI 边界是未定义行为。
   改成 `strtoull` + 全串校验，非法 id 返回错误字符串。
4. **`deviceAlive` 把"读取失败"和"设备已消失"混为一谈**（MINOR）。一次瞬时读失败会
   把 `lost` 永久置位，且没有任何路径清除。改成返回"能否回答"，只有确定不在才算丢失。
5. **监听安装失败是静默的**（MINOR）。现在 `NAE_TRACE` 下会打印。
6. **`queryCaps` 的稳定等待在 `0 == 0` 时提前结束**（MINOR）——设备切换中途正是回报 0
   的时候。改成需要两次相等的**非零**读数。
7. **DoP 载波算出来又被清零**（MINOR），宿主看到"有载波、但 dopSupported=0"。
   两者一起清零，因为这条路只有 float32。
8. **析构顺序**：恢复采样率时 AudioUnit 还持有设备（MAJOR）。改成先 dispose unit，
   再释放 hog，最后恢复速率——正好是 `open` 的逆序。

CMake 许可门禁：

9. **读不出许可证被当成 LGPL**（MAJOR）。`execute_process` 没取返回码，ffmpeg 起不来时
   输出为空、两个 `MATCHES` 都不成立，于是"通过"。现在非零退出或空输出直接失败。
10. **门禁读的是缓存里的旧二进制**（MAJOR）。`find_program` 会缓存结果，改了
    `NEIRO_FFMPEG_ROOT` 之后仍在读旧树。改成不缓存的解析。
11. **CLI 与库可能不是同一次构建**（MAJOR）。现在比较 CLI 报告的 `libavcodec` 主版本
    与将要链接的库文件名，不一致即失败。
12. **日志说谎**（MAJOR）：打印"使用 vendor 树"而实际缓存仍是系统包。改成打印实际使用的根。

Base：

13. **重命名文件后 `tags` 行不跟随**（BLOCKER）。`rewrite_path` 更新了 tracks/
    playlist_entries/files，漏了 tags，于是列表里留着旧路径、新路径缺席。已补。
14. **删除的文件永久留在索引里**（BLOCKER）。`apply_scan` 只删 `files` 行。已补。
15. **没有 library 时四个浏览查询返回"空列表"**（MAJOR），与本文件自己的约定
    （"每个 library 命令都要报告这一点，而不是假装答案是空的"）冲突。改成报错。
16. **`list_artists` 用二进制排序数专辑，`list_albums` 用不区分大小写分组**（MAJOR），
    两个界面会对不上。已统一。
17. **搜索只折叠 ASCII**（MINOR），搜 "bela" 找不到 "Béla"。加了 Rust 侧折叠的
    `search_text` 列，查询与它比较。
18. **`index_tags` 永远刷新不了**（MINOR）：`index_paths` 跳过已有行，命令既不生效也不发事件。
    改成先删行。
19. **关停时在途的索引行被丢弃**（MINOR）。加了 2 秒上限的收尾 drain。
20. **探针测不到扫描索引这条路**（MAJOR，测试缺口）：原来先用 Base 写标签，
    扫描时全部"已索引"被跳过，把扫描那一行删掉探针仍然全绿。
    改成用 lofty 直接写标签、先扫描、再单独验证写入路径。

## 5. Ponytail 审查

### 这个仓库是什么

一个 C++ 音频引擎（解码、DSP、设备输出）通过 C ABI 暴露，加一层 Rust 的 Base
（曲库、播放列表、标签、扫描、远程服务器）再通过 C ABI 暴露，加一个 Rust 的
engine binding。假设负载：**单机、单听众、一个输出设备、曲库约一万首**。

### 必须修

**1. `nae.cpp` 里同时住着两个后端**（`engine/nae.cpp`，7,688 行）
- 是什么：WASAPI 与 CoreAudio 在同一个文件里用 `#ifdef _WIN32 / #else` 分隔。
- 问题：本轮 macOS 的重采样修复在两个 `#else` 块里，离 WASAPI 的同等逻辑两千行远。
  一个漏掉的守卫在另一端静默地构建出错误的东西，而两端都要跑一遍验证才会发现。
- 修法：按 ROADMAP P0-A 把后端移出 `nae.cpp`，落到 `AudioBackend` 接口后面，
  一个后端一个编译单元。
- 不修：每次平台改动都继续付一次跨平台验证的成本，且失败时看不出是哪一端。

**1b.（已处理）Windows 的 `AudioBackend` 实现是绕回自己导出的空壳**
- 是什么：`WasapiBackend` 的 `enumerate`/`queryCaps`/`open` 分别调用
  `NAE_EnumerateDevices`、`NAE_QueryDeviceCaps`、`NAE_OpenFile`——也就是本 DLL 的导出。
- 问题：接口的两个实现里，一个（CoreAudio）是真正的设备层，另一个（WASAPI）是
  把调用绕回同一份代码的包装。这既让"一个接口、两个后端"这句话在 Windows 上不成立，
  也让拆分看起来完成了一半。目前只有 `backend_check` 用它，引擎的打开路径没走它，
  所以还没有循环调用；一旦有人把引擎接到这个接口上，就是自己调自己。
- 已做：文件删掉了，适配器搬进唯一的使用者 `backend_check.cpp`，引擎的源列表回到
  `nae.cpp` + `session.cpp`。删掉的是"看起来实现了接口"的假象；WASAPI 的设备代码
  仍在 `nae.cpp`。
- 已做（后续一轮）：真正的 Windows 后端。`WasapiOutputStream` 拥有
  `IAudioClient`/`IAudioRenderClient`/事件句柄/协商到的格式，不读 `NAE_Handle`；
  `openWasapiStream` 与 `openCoreAudioStream` 同形；渲染循环两端只有一条设备路径。
  端口的两个坑写进了交接：`SetEventHandle` 必须在 `Initialize` **之后**；
  这台机器的端点拒绝事件驱动的独占 `Initialize`，回落到定时器节奏是显式行为。

**2. 索引写入仍是"每条一次 SQL"**（`base/src/control.rs: drain_index`）
- 是什么：扫描后每首歌一行读进 `tags`。
- 问题：本轮已把一批包进一个事务、把进度事件从每行一次改成一撮一次，
  但单条写入仍然是独立语句。一万首的首次扫描期间，控制线程要处理一千次事务。
- 修法：已经是批量事务了；剩下的是把 `put_tags` 的单条路径也走批量包装。
- 不修：首次扫描期间宿主发出的命令会被推迟到秒级。

（第 2 条本轮已修到"一撮一个事务"，剩下的是完整性收尾。）

### 应该修

**3. `base_probe` 的等待预算是固定的 5 秒**（`base/src/bin/base_probe.rs`）
- 是什么：队列编辑段等"入队生效"用 5 秒。
- 问题：设备在一次策略变更里重开就要 400–850 ms；几张命令排在它后面，
  5 秒会被真实耗时吃掉。本轮出现过一次。
- 修法：把这类等待从"固定预算"改成"观察到前一条命令的后果"。
- 不修：偶发红灯会被当成回归。

**4. 两个 transport serve loop 是复制**（`base/src/transport/{mod,unix}.rs`）
- 是什么：Windows 与 Unix 各一份约 60 行的循环。
- 问题：已明确记录为决定（读原语不同，抽 trait 的收益低于风险）。
  按 Ponytail 的规则，带说明的决定不算问题——留在这里只为让下一个人知道我看见了。

### 可以更好

**5. `list_tracks`/`search` 的 `limit` 已加上 500 上限**（本轮）。宿主需要更多就翻页。

**6. macOS 的 `macos_play_check` 需要一个音频文件**，而仓库不存音频。脚本现在
诚实打印"not run"而不是失败——但这也意味着 macOS 的播放检查在干净构建上不会自动跑。

### 结论

- Verdict: **可以用，但 `nae.cpp` 的双后端结构是下一个必须处理的债**；
  Base 的索引本轮已经能承载一万首，剩下的是一致性收尾。
- Lean: 两个 transport 循环（约 60 行）是唯一明显的合并候选，已记录为有意保留。
- Not checked: `remote.rs`（1,620 行，Jellyfin/Navidrome 客户端）、`tag.rs` 的写入路径、
  Windows 的 WASAPI 后端、Android/iOS 的后端；没有在 GitHub runner 上跑过工作流。

## 5.5 第一步（拆双后端）已执行

报告初稿把"拆 `nae.cpp` 的双后端"列为第一步，随后按此执行：

- `NAE_Handle`（627 行）连同它旁边的 seam 常量与 `StreamFormat` 移到
  `engine/nae_internal.h`；
- macOS 的设备打开与默认设备查询移到 `engine/open_coreaudio.cpp`，该文件
  只编进 macOS 目标——Windows 根本不编译它，改动无从影响另一端。

`nae.cpp` 里剩下的 `#ifndef _WIN32` 只有两处，都是函数内分支而非后端实现：
设备枚举的 JSON 半段（与 Windows 半段共用同一段 malloc 收尾），以及把
`neiro::OutputStream` 适配成渲染循环所读状态的包装结构。

**顺带发现一个真缺陷**：`NAE_GetEngineCapabilities` 在 macOS 上仍把
`shareModes` 过滤成只有 `shared`，注释理由是"CoreAudio 的
`exclusiveSupported` 是 0"——这条在 hog 成为本平台独占之后就不成立了。
结果是引擎对外宣称的可用模式里没有 exclusive，而设备列表说设备支持它；
宿主读 `shareModes` 就永远不会走独占路径（`hog_mode_check`、`macos_play_check`
用的正是这条路）。现在两种模式都列出，与 `exclusiveSupported=1` 一致。
